# Mercury Pre-Login Key Establishment

## Executive Finding

**The random 4-byte default key is confirmed, by both static trace and a decisive live
experiment, to be the ONLY key ever active for a connection's first LoginReply.** There is
no earlier Mercury message, no earlier key-installation path, and no RSA/LogOnParams
relationship that establishes or carries the Blowfish key before this point. A live,
falsifiable test — two consecutive login attempts on the *same, unrestarted* process —
produced **two different garbled BaseApp addresses** (`160.211.122.84:14454` then
`255.255.255.255:65535`), **proving the random key is regenerated fresh on every
`ServerConnection::logOnBegin` call**, not once per process as an earlier hypothesis in
this same pass initially (and incorrectly) suspected from static evidence alone. This
document corrects that intermediate hypothesis with direct capture evidence, consistent
with this project's standing practice of reporting corrections rather than silently
discarding them.

## Confirmed Initial Key

Unchanged from `MERCURY_ACTIVE_DECRYPT_TRACE.md` and `MERCURY_KEY_STATE_LIFECYCLE.md`,
re-verified this pass:

- Generated by `RAND_bytes(buf=this+0x11, len=4)` inside `0x988cf8`.
- Installed into a fresh `BF_KEY` (`this+0x30`) via `BF_set_key`.
- Reached through the unconditional chain `0x917070` → `0x93a620` → `0x988cf8`.

**NEW this pass**: this chain's *own* caller was traced one level further —
`0x917024`'s only caller is `0x92c704`, inside a constructor-shaped function whose real
entry is `0x92c430`, which itself has exactly one caller, `0x8e7244` (inside a function
starting at `0x8e7098`, which has **zero** discoverable static or virtual callers in the
binary). Statically, this looked like a one-time, lazily-invoked singleton constructor,
separate from `ServerConnection::logOnBegin`'s own code (`logOnBegin`'s log call resolves
to `0x93c108`, in a completely different code region). **This static appearance is
misleading on its own** — see the live experiment below, which proves the *practical*
effect is a fresh key every login attempt regardless of the exact call-graph shape (most
likely explanation, not separately re-verified: the object holding the `EncryptionFilter`
is itself torn down and reconstructed as part of each `logOnBegin`/`ServerConnection`
setup cycle, even though the specific constructor function is reached indirectly).

**New observation this pass**: in the second (same-process, no relaunch) login attempt,

for distinguishing "per-process" state (RSA public key loading) from "per-attempt" state

but directly observed.

## Pre-Login Mercury Message Timeline

Built from this project's own genuine wire captures (`MERCURY_WIRE_CAPTURE.md`,
`MERCURY_SOCKET_READ_TRACE.md`, and every `strace`/`tcpdump` session across this entire
investigation) rather than assumption:

| Order | Direction | Message ID | Length | Purpose | Encrypted? | Key State |
|---|---|---|---|---|---|---|
| 1..10 | Outbound (client→LoginApp) | LogOnParams (LoginInterface msgID, not yet mapped to the ClientInterface table this project decoded) | 273 bytes | Credentials (RSA-OAEP encrypted `{flags, 3 strings}`) + cleartext framing | RSA only; **not** Blowfish | N/A — Blowfish key not used for outbound requests at all (no code path feeds LogOnParams data through `BF_ecb_encrypt`) |
| 11 | Inbound (LoginApp→client) | `0xFF` ("Reply") | our test: 25 bytes (real server: unknown) | LoginReply: replyID + status + 20-byte BaseApp-address body [+ optional key-update block] | The 20-byte body, yes (Blowfish) | **STATE 0's random key** (proven above) |

**CONFIRMED, not assumed**: across every wire capture this project has ever taken
(spanning many prior passes, using both a real client against a fake LoginApp and
extensive `strace`/`tcpdump` instrumentation), the client **retries the identical
LogOnParams request** every ~0.4 seconds and receives **no other inbound traffic of any
kind** until either a Reply arrives or the connection times out. **There is no earlier
inbound Mercury message in this protocol phase** — LoginReply is unambiguously the first
and only inbound packet type, answering this task's Phase 3 question directly: **there is
no earlier opportunity for a key to be installed via any inbound message**, because no
earlier inbound message exists.

## LogOnParams / RSA Relationship

**CONFIRMED NEGATIVE, via direct code inspection, not inference**: `BF_set_key`'s only
three callers in the entire binary (`0x9889e8`, `0x988cf8`, `0x988be8`, exhaustively
enumerated across the two preceding passes) each source their key material from either
(a) a caller-supplied `std::string&` argument with no connection to `LogOnParams`, (b) a
freshly-generated `RAND_bytes` buffer, or (c) the object's own pre-existing stored string.
**None of the three ever reads from a `LogOnParams` object, its fields (`+0x10`
string A, `+0x28` string B, `+0x40` string C, `+0x58` numeric field, `+0x5c` digest), or
its RSA-encryption code path** (`0x9d8014`/`0x9d8018`, per `LOGONPARAMS_SERIALIZATION.md`).

Therefore, definitively:

- The Blowfish key is **not** sent to the server inside `LogOnParams`.
- The Blowfish key is **not** encrypted inside `LogOnParams`'s RSA payload.
- `LogOnParams`'s RSA-encrypted region and the Blowfish default key are **structurally
  unrelated** — confirmed by the complete absence of any code path connecting them, not
  merely by failing to find one.

This resolves this task's Phase 7 with a clean negative result: **(unrelated to LoginApp
authentication)** is the correct classification among the options offered, with the
caveat that "unrelated" here means "not connected via any code path found in this binary,"
not "impossible in principle for some other build."

## Active Key at LoginReply Decryption

**CONFIRMED, twice over — statically and empirically:**

1. **Statically** (`MERCURY_KEY_STATE_LIFECYCLE.md` §5/§6): `onLoginReply`'s own
   instruction ordering calls decrypt (`0x938234` → `0x989600`) *before* it ever reads or
   checks for the `0x32ef9816` marker (`0x938278`+). A same-message key update, even if
   present, cannot retroactively re-decrypt bytes already processed earlier in the same
   function.
2. **Empirically, this pass**: two consecutive login attempts in the same unrestarted
   process decoded **different** garbled addresses from **byte-identical** plaintext
   input, directly proving the key differs between attempts — consistent only with "fresh
   `RAND_bytes` key per `logOnBegin` call," and inconsistent with any hypothesis
   involving a stable, reused, or predictable key.

## Final Determination

1. **What is the earliest known key installation?** The `RAND_bytes(4)`-seeded default,
   installed during `ServerConnection`'s `EncryptionFilter` construction, which this
   pass's live experiment shows effectively happens **fresh on every `logOnBegin` call**
   (not once per process, correcting this pass's own initial static-only hypothesis).
2. **What exact function performs it?** `0x988cf8`, called via `0x93a620` ← `0x917070`.
3. **What is the key source?** OpenSSL `RAND_bytes` — a cryptographically random value,
   generated locally, never transmitted.
4. **What is the key length?** 4 bytes (32 bits), a hardcoded literal.
5. **Is there a later key replacement before LoginReply?** **No** — proven both
   structurally (no inbound message exists before LoginReply) and by direct code order
   (the only replacement mechanism, `0x32ef9816`, lives inside LoginReply itself and runs
   after that same message's body is already decrypted).
6. **What key is active when the LoginReply body is decrypted?** The random default key
   from step 1/2/3/4, with certainty.
7. **What evidence proves it?** A gap-free static instruction trace (this pass and the
   prior one) **plus** a decisive live experiment this pass: two same-process login
   attempts with identical plaintext input produced two different decoded addresses.
8. **What is still unknown?**
   - The precise mechanism by which `0x917024`'s construction chain gets re-invoked on
     every `logOnBegin` despite being reached through a call graph that looks, in
     isolation, like a one-time lazy singleton — not fully traced this pass (the live
     evidence proves the *effect*; the exact re-construction/re-entry mechanism was not
     pinned to a specific instruction).
   - Why `PublicKeyCipher::setKey`'s log line did not repeat on the second attempt while
     the Blowfish key clearly did change — suggesting these two pieces of per-connection
     state are managed by different lifetimes within the client, not fully explained at
     the code level.
   - Whether the `255.255.255.255:65535` result (all bits set) from the second attempt
     indicates a distinct decrypt-failure fallback/sentinel path rather than "successfully
     decrypted garbage" like the other observed results — not investigated, flagged as a
     minor curiosity.
   - Everything already flagged UNKNOWN in `MERCURY_KEY_STATE_LIFECYCLE.md` §9 remains
     unknown (the 32 unresolved `+0x30` write sites, `0x988be8`'s callers, genuine
     server-side behavior).
9. **What is the single highest-value next investigation?** Determine whether the
   `EncryptionFilter`/key-generation object is destroyed and recreated on every
   `logOnBegin`, or whether only its *key* is regenerated while the object persists —
   this would refine (but, given the already-conclusive live evidence, not overturn) the
   "fresh key per attempt" finding, and would require either live object-address capture
   (this project's `DEBUG_BADFLAGS`-style live-pointer technique, previously proven) across
   two attempts, or a deeper static trace of exactly how `0x8e7098`'s construction chain
   gets re-entered.
